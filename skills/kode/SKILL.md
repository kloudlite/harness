# Kode

Kode (Kernel for Orchestrated Development and Execution) is the infrastructure that an agent owns for development and execution. You are not a process in one folder. You make isolated machines, compose services, send real traffic to your code, save state and remove all of it. Compute is the cheapest thing you have. Idle compute, stored data that nobody reads and used quota are the expensive things.

This is the one Kode skill: the definitions, the rules and the way to choose. It gives no fixed steps for a task; you compose them. The `references/` folder holds the depth: `tools.md` (every tool and argument, ids and states), `permissions.md` (who may call each action), `models.md` (which model class each agent gets), `worker-templates.md` (the briefs and the hand-off report), `use-cases.md` (14 worked cases and how to compose a new one), `memory.md` (the sections of the project memory, how a task starts from it, how to draft it when there is none, and a full example), `planning.md` (the plan file for work that is split), `pipelines.md` (the definition format), `services.md` (common services with ports and mounts), `devices.md` (workspaces on the person's Mac), `processes.md` (background processes, right and wrong, as tool calls), `errors.md` and `setup.md` (installing, and which host serves which tools). When the Kode tools are present, code runs in a workspace, not on the user's computer, whatever the request says.

## Solo quick path

The default: one session, one workspace, nothing delegated.

1. `status`; `memory` `read`: it says which repository, base, desk and environment the task needs (`references/memory.md`); `volume` `list` with the project `label`.
2. `workspace` `fork` from `name@base` with a `name` and `ttl_secs`.
3. Pull (and check out the git branch that `open-work` names, if any), work, test.
4. Push: merged, or unfinished on a git branch on origin. A code change alone is no reason for a volume commit: code reaches the next session through git (pushed to origin, unfinished work on a git branch; the next workspace pulls it). Remove credentials from the home.
5. `memory` `write`: every section the work changed; `workspace` `delete`. It takes no snapshot by default, and that is the normal end: the code is in git, the workspace is discarded. Pass `save: true, tag: "base"` for a structural change, where it is required (convention 8: dependencies or libraries, packages, the folder structure, the git sources, variables), from the clean merged default branch with the build passing, and only while `base` is still the snapshot you forked from (convention 9). A plain delete refuses, naming the difference, when packages, image or variables changed since that snapshot: then `save: true` or `skip_snapshot: true`. The volume stays.

## Glossary

One word, one meaning. All work runs in the context of one team: a person's own team or a shared team. A team is not a component.

1. **Session.** Your conversation and its context. It runs outside Kode and drives it with tools. One session can control many workspaces. A session is not a workspace: the workspace holds code, the session holds history.
2. **Workspace.** An isolated machine in the cloud with its own kernel and a home (`/home/kl`) kept while stopped: source in `~/workspace`, installed software, caches, configuration. Code is edited and run here. Its package list (nixpkgs names with their pins) is part of each snapshot, so a fork starts ready. A workspace is one container with one home and is itself the working tree: a second line of work is a second workspace, forked. Standalone, or managed by a desk.
3. **Environment.** A set of named services that run together, each from a container image, reachable by name and port (`db:5432`). One disk holds the data of mounted folders. It is defined as data, or forked from an environment or a snapshot.
4. **Desk and netgroup.** A desk is one piece of work, private to its creator; the tools act in it. Its **netgroup** is the network side: the workspaces and capsules joined to the one environment they reach (or none), the intercepts held there, and one idle clock. Every desk owns one (`netgroup-desk-…`); a person also makes netgroups without a desk (`ng-…`, `kode netgroups create`) and joins a standalone workspace to one (`kode netgroups join`), a device one too. Teammates use their own netgroups on the same environment. Netgroups are replacing desks; the tools still name the desk.
5. **Intercept.** Sends all traffic of one environment service to a workspace of the netgroup (the desk's); the service pauses; callers keep the same name and port. Environment-wide. A stopped workspace gives the traffic back, but the intercept stays recorded and takes hold again when the workspace returns: only `intercept` `stop` ends it.
6. **Process.** A command the workspace's tool server started and lists in `process` `list`: every `exec`, and a **background process** (`exec` with `detach: true`, or one past its `soft_ms`), such as a dev server or a watcher. You keep working while it runs, and an intercept sends traffic to it. While one runs, the workspace stays awake. It lives only while the workspace runs. A command left behind inside an exec with `&`, `nohup`, `setsid` or a daemon's own fork is **untracked**: unlisted, it keeps nothing awake and ends with its exec.
7. **Capsule.** A disposable isolated container that runs one command and ends when it exits (default 300 s, at most 24 h). In a netgroup (a desk's) it reaches the environment. Files are gone at the end. It is never where an agent works; that is a workspace.
8. **Volume, disk, snapshot, tag and label.** A volume is the saved storage of a project's base, and everything in it is counted together. It holds **disks** and **snapshots**, nothing more. A disk is the live, editable storage of one workspace or environment, attached to at most one. A **snapshot** is a read-only copy of a disk at one moment, with its definition (the package list, or the services and their configuration); `workspace` or `env` `snapshot` makes one, and a named volume numbers them `v1`, `v2` (`name@N`). A **tag** is a name on one snapshot, unique within the volume, such as `shop-code@base`; it moves only when you ask (`snapshot` or `delete` with `tag`, or `volume` `tag`). A fork and a start from a snapshot add a new disk to the same volume; only an empty create makes a new volume. A tagged snapshot does not expire and cannot be deleted; an untagged one expires 30 days after it was made or last forked from. A volume's first snapshot is tagged `base` when it names no tag. `labels` and a `description` are words on the volume for finding it. A reference is `name@<tag>`, `name@N`, `name` (its `base` snapshot, else its newest) or a snapshot id. There is no lineage to read: snapshots are ordered by number, and nothing merges (convention 9).
9. **Pipeline.** A versioned JSON definition of jobs in a graph; each job runs its steps in its own capsule; a run starts one version by hand, on a schedule, from a webhook, or after another pipeline.
10. **Secrets and variables.** A variable is `NAME=value` in the `env` of a workspace, service, capsule or job. A secret is a named value of an owner; a variable refers to it as the whole value `${{ secrets.NAME }}`. No one reads a value back.
11. **Connector.** A link from an owner to a code host (GitHub, GitLab) or a container registry: clone over HTTPS, push to github.com with the person's linked GitHub account, image push and private pull. Connected in the web console.
12. **Memory.** The current structure of a project and the guide every task starts from, kept by the `memory` tool in eight sections of the team, in reading order: `architecture`, `sources`, `run`, `environments`, `volumes`, `desks`, `conventions`, `plan`; and `open-work`, yours. It names only what lasts: `desks` is the layout of work (which desks, their workspaces and environment), never a live desk, workspace or running environment. A project is its owner, a team or a person's own account: a team with several repositories shares one memory, with a heading or bullet for each inside a section. It says what is, never what happened.
13. **TTL and quota.** A TTL (`ttl_secs`, 10 minutes to 30 days) deletes a workspace, environment or desk that stays unused past it; `create` and `fork` take it in the same call. Quota is the owner's ceiling on workspaces, environments, snapshots, capsules, disk, cpu and memory; the `quota` tool reads it. Choose the size for the job when you create or fork (`cpu`, `memory_gb`; default 4 CPU / 8 GB): a snapshot carries no size. A Rust build of a large base such as `kode-platform` forks with `cpu: 8, memory_gb: 16` and builds with `-j 6`. `resize` changes a running workspace, and the new size applies at its restart.

**"Sandbox" is not a Kode object.** It is the general idea, not a resource. When the user asks for a sandbox, give a workspace, unless they ask for one command or a throwaway run, which is a capsule.

**If you know git.** The storage of a workspace or environment works like a repository of whole machines.

| git | Kode |
|---|---|
| repository | volume |
| commit, tag, topics | snapshot (`vN`), tag (`name@base`, `name@node-22`), `labels` |
| `git checkout base` | `workspace` `fork` from `name@base` (an environment: `env` `fork` with `snapshot_id`) |
| `git commit` / `git commit` + `git tag -f node-22` | `snapshot` (untagged) / `snapshot` with `tag: "node-22"` |
| `git tag -f base v4` / `git tag -d node-22` | `volume` `tag` / `volume` `untag` (or `snapshot` `tag` / `untag`) |
| renaming the repository | `volume` `rename` with `to`: every snapshot, tag and the history stay; the old name stops resolving, so update `memory` and every note or script that spells `old@…` |
| `git checkout v2` to look at an old state | `workspace` `fork` from `name@2`: a new disk in the same volume, nothing moves |

Three facts decide every topology choice:

1. **Managed vs standalone.** A workspace created in a desk is managed: it reaches the environment, and the desk starts, stops and deletes it. A standalone workspace never joins a desk; the person can join it to a netgroup from the laptop (`kode netgroups join`). `workspace` `fork` (from a live workspace in `source` or a snapshot in `snapshot_id`) makes a new workspace that joins the desk the tool acts for, so it is managed, while a fork made from the laptop CLI (`workspaces clone`, `workspaces restore`, `devices workspaces clone`: the CLI keeps those names) is standalone. To fork into a desk from the laptop, use `kode desks clone-workspace WORKSPACE --to NAME` (a device workspace also needs `--snapshot ID`).
2. **A capsule ends.** It is for one command; nothing in it survives. A capsule in a desk is a managed member and reaches the environment.
3. **An intercept is environment-wide.** Every caller of the service, every teammate's desk included, reaches the workspace. One workspace per service.

```
team ─┬─ desk ── its netgroup joins ──> workspaces, capsules ──> environment (0 or 1)
      │                         intercept: service ──> workspace of the desk
      ├─ environment ── services (image, ports, env, mounts)
      ├─ volume ── disks, snapshots name@N, tags name@base <── workspace, environment, job (saveTo, fromSnapshot)
      ├─ pipeline ── versions ── runs ── jobs (one capsule each)
      ├─ secrets ──> env of a workspace, service, capsule or job
      └─ connectors ──> git clone and push; image push and pull
```

## Invariants

1. **Packages.** Never `apt-get`, never pipe `curl` into a shell, never install system-wide. Use the `packages` tool (nixpkgs) first. Only what nixpkgs lacks goes into the home folder, where it persists. `python3` is in every workspace; a workspace that lists its own Python (`python312`, `python3@3.11`) gets that one instead. Python libraries: `packages` `add` `uv`, then `uv venv .venv && uv pip install <lib>`, run with `.venv/bin/python` (there is no `pip` beside `python3`).
2. **Two end states.** Each resource that you create ends as one of: **snapshotted, then deleted** or **deleted**. A code change alone is no reason for a snapshot: code reaches the next session through git (pushed to origin, unfinished work on a git branch; the next workspace pulls it). A snapshot is made only for a structural change to the workspace, and then it is required (convention 8). Volumes never merge: when `base` moved since you forked it, let go of your volume state (convention 9). `workspace` `delete` deletes without a snapshot by default; `save: true, tag: "base"` snapshots and moves `base` onto it first, from the clean merged default branch with the build passing (convention 8). A plain delete refuses, naming the difference, when the workspace's packages, image or variables changed since the snapshot it was made from: decide then, `save: true` to keep them or `skip_snapshot: true` to drop them. Ordinary code changes need no save: bases are refreshed nightly by pipelines that pull the latest code. Forks, capsules, copies of an environment and one-off checks are throwaway: deleted without a snapshot. Stopped is a pause inside a session, never an end.
3. **Start from a snapshot, end clean.** A session starts from a snapshot, and nothing that runs or is stopped stays between sessions. Start with `workspace` `fork` from `name@base` (an environment: `env` `fork` with `snapshot_id`); then pull, and check out the git branch that `open-work` names. End with the work pushed (merged, or on a git branch on origin), the base refreshed by `workspace` `delete` with `save: true, tag: "base"` only when the environment changed (convention 8), the memory updated, and every workspace and environment that you created deleted. Conventions 15 and 16 give the order. The first session of a project has nothing to fork from: use case 13.
4. **One volume per base.** A project keeps one volume for each kind of base it reuses (a component's toolchain, a test fixture, an environment's data), each named in the memory. Forks and starts from a snapshot add disks to the same volume, and their snapshots go there too. Never make a second volume of the same base and never delete a volume to end a session: a snapshot stores only the blocks that changed, a second volume stores a full copy. Only a workspace or environment that was created empty makes a new volume, and a new kind of base is agreed in the memory's `plan` first. Keep `base` on a good snapshot: untagged snapshots expire after 30 days, and a volume whose snapshots all expire is gone.
5. **Ownership.** The coordinator has full freedom over what it created in this desk: start, stop, snapshot, fork and delete it without a question to the user. A worker uses the workspaces it was given and leaves their lifecycle to the coordinator. What you did not create (a team environment, a named volume, a saved pipeline, the objects of another desk, what the user had) is for the coordinator only. Ask the person only for what cannot be undone: `env` `restore`, the delete of a shared environment or of a volume, and an intercept on an environment that other people use.
6. **Legible.** Each object that outlives your session has a name that a person can read, and a `task` or `message` that says why it exists. Each volume has a `description`, `labels` and a `base` tag. Keep a small declared set (named volumes, saved pipelines), not a store that nobody can read.
7. **Secrets.** Never print, echo, log or repeat a secret value. Pass it to `secret_set`, never in a command line or a chat message. Refer to it by name. Never run `env`, `printenv` or `set` in a workspace: its secrets are variables there (a value a tool answers is masked as `***`, a variable's name is not).
8. **Refusals.** When a call fails or is refused, a quota refusal included, report the error as it is. Do not go around it through another desk, workspace or tool. A worker stops and reports to the coordinator.
9. **Status first.** Call `status` at the start of each turn. It lists the processes that crashed, the restarts and what runs in the desk. Never assume that a background process still runs.

## Conventions and discipline

A checklist of practice. Each rule holds in every topology, and the rest of the skill refers to it by number.

1. **Names.** 1 to 40 lowercase letters, digits or `-`, starting with a letter, unique per owner. Workspace: the repository or component (`api`). Fork: `<source>-<stream>` (`api-auth`), with a `task` that says what it is for. Environment: the app and purpose (`shop-dev`, `shop-pr-42`). Desk: the piece of work (`orders`). Pipeline: what it does (`api-ci`). Git branch: the stream name of the plan file. Tag: the good state it names (`base`, `node-22`, `before-migration`).
2. **Volume names.** `<project>-base` for a workspace volume, `<project>-env` for an environment volume. Never the name of a live environment: `env` `create` reads `source` as an environment first.
3. **Labels** say what a volume is, so that `volume` `list` with `label` finds it: the project name, and `test` for a fixture. At most 8. A `labels` value replaces the whole set: repeat the ones to keep.
4. **Tags.** `base` is the good state a session starts from, tracking the latest default branch: only snapshots whose build or test passed get it, and only the coordinator (or the solo agent) moves it, with `snapshot` or `delete` `save: true` and `tag: "base"`. Other tags name other good states (`node-22`, `before-migration`). A tag moves only when you ask; a snapshot without a tag moves nothing. Addresses: `name@<tag>` and `name@N`; numbers are unique per volume and never reused. Unfinished code is a git branch on origin, never a tag. A volume holds at most 16 tags: remove the ones nobody starts from.
5. **Who moves `base`.** Practice, not a platform rule: the coordinator, or the solo agent; both do the refresh. A worker never tags `base`; it snapshots only when its task asks, and only with the tag the task names. A base that no session touched still drifts: recommend one scheduled pipeline per base that pulls, builds and saves it (`saveTo: name@base`, `references/pipelines.md`).
6. **Snapshot `message`.** Required on every `snapshot` (the tool refuses one without): what changed since the last snapshot and whether it is good (`node 22, deps of 2026-11-16, build passes`). A snapshot made without words gets a generated one (a pipeline save names its pipeline, run, job and starting snapshot).
7. **Volume `description`** (at most 500 characters). What is inside (repositories, toolchain, data) and what to use it for. Give a new one when the contents change.
8. **When to update the base.** Two cases, nothing in between. **Code only:** push it to git and discard the workspace: `workspace` `delete` saves nothing. Unfinished code goes on a git branch on origin, and `open-work` names the repository, that git branch and what is left; the next session forks `name@base`, pulls and checks it out. **A structural change to the workspace:** updating the base is required, not optional. Structural means: dependencies or libraries updated (a lockfile, a vendored lib, their warmed build cache); packages added, removed or upgraded; the folder structure changed (a checkout moved or renamed, a directory layout the tools rely on); the git sources changed (a repository added, removed or renamed, or pointed at another remote or default branch); variables or the image changed. Left unsaved, such a change makes every later session start from a base that no longer matches the code. **Refresh the base:** once the work is merged into the default branch (`main`/`master`), check out that merged branch (clean tree, no feature branch), run the base's build or test step, remove credentials from the home, check that `base` is still the snapshot you forked from (`workspace` `get` `disk.from` against `base` in `volume` `get`), then `workspace` `delete` with `save: true, tag: "base"`: it snapshots, moves `base` onto it, then deletes; pass a `message` naming what changed and that the build passed. When `base` moved since your fork, do not save over it: redo the change on a fresh fork of the new `base` and save that (convention 9). A failed build moves no base: fix it, or delete with `skip_snapshot: true` and name the unsaved change in `open-work`. Only a call that names `tag: "base"` moves it: give it only on a good state. A plain `delete` refuses when packages, image or variables changed since the base: that is a structural change, so refresh the base; `skip_snapshot: true` only drops a change you mean to throw away. The nightly refresh pipelines pull the latest code and cover code only.
9. **No merge.** Two disks never merge, and a newer `base` already holds what came after yours. When `base` moved since you forked it (`volume` `get` shows `base` on a newer snapshot than your `disk.from`), your volume state is stale: push the code, delete the workspace with `skip_snapshot: true`, and `snapshot` `delete` any untagged snapshot you made. Never move `base` back to yours. When your structural change is still needed, fork the new `base` into a fresh workspace, redo the change there (packages, variables, setup), build, and save that. To go back to an older state, fork from that snapshot (`name@N`); for an environment, `env` `restore`. Nothing else rewinds.
10. **Storage.** A snapshot stores only the changed blocks and uses one snapshot slot (20 for a person, 80 for a team). An untagged snapshot expires 30 days after its last use; delete it sooner with `snapshot` `delete` when nothing needs it. A tagged snapshot is refused by `snapshot` `delete`: untag it first, and never delete the snapshot `base` is on. Every disk counts in its volume until its workspace or environment is deleted.
11. **TTL.** Every workspace, environment and desk gets a TTL: `ttl_secs` in the `create` or `fork` call. It is a backstop: an environment is not expired while a desk is connected to it, and a workspace or desk only once its desk is idle. You still delete at the end.
12. **Never in a snapshot or the memory.** No credential in the home before a snapshot: no token file, kubeconfig, registry login, `.npmrc` or `.env` with a value. Every member of the team can fork a team volume. The memory names a secret, never its value.
13. **Memory content.** `architecture`: each component, what it calls, where it runs. `sources`: each repository, its branch, its path in a workspace and how changes leave it. `run`: the packages and commands to build, test, run and ship. `environments`: each environment's `volume@tag`, services, seed data and reset. `volumes`: each volume, what is inside, its labels and the tag to start from (`shop-code@base`). `desks`: which desk and workspaces each kind of work uses. `conventions`: the team's rules. `plan`: the agreed plan with the state of each step. `open-work` (yours): each unfinished item with its git branch on origin (`shop-api` `feat/auth`) and what is left. Volume tags, never snapshot numbers. The template of each section and a full example are in `references/memory.md`.
14. **Memory hygiene.** Current state, never history, and short (a section holds at most 16 KiB). Only the coordinator writes: read it first, write it last, patch with `edits` and the `if_version` of your read, and on a `409` merge and write again. Each tool answer carries `memory: {rev, changed}`; when `changed` is true another session wrote it: read it again before you rely on it. Keep it current: a task that changes the project patches the sections it changed in the same session, and removes what no longer exists.
15. **Start of a session, in order.** `status`; `memory` `read`; `volume` `list` with the project `label`; `volume` `get` to see that the tag is there; `quota`; `workspace` `fork` from `name@base` with a `name` and `ttl_secs`; pull, and check out the git branch that `open-work` names. When the memory is empty and no volume carries the label, this is the first session: brainstorm with the person, write the initial draft and agree it, then use case 13 (`references/memory.md`).
16. **End of a session, in order.** Stop every intercept. Commit and push; merge, or leave unfinished code on a git branch on origin. Remove credentials from the home. After a structural change (dependencies, packages, folder structure, git sources, variables), refreshing the base is required (convention 8): the clean merged default branch checked out, its build or test passed, and `base` still the snapshot you forked from. After code only, save nothing. `memory` `write`: every section the work changed, not only `open-work`. Delete each workspace and each environment that you created: `workspace` `delete` takes no snapshot by default, `save: true, tag: "base"` snapshots and moves `base` first, `skip_snapshot: true` drops packages, image or variables that changed since the base when a plain delete refuses. The normal end saves nothing. Read the answer's `saved`: it says which tag is on the snapshot, or that it is untagged. Say what was removed and what was kept. Nothing stays, running or stopped.
17. **Claims.** A claim that something works carries the command, its exit code and the end of its log. "Not verified" is an allowed answer.
18. **Hand-offs are artifacts:** a pushed branch, `REPORT.md`, a plan file, which the report names. Never the context of a conversation.
19. **Before you spend.** Read `quota` before a fan-out. Write one plan file with the contracts before parallel work starts (`references/planning.md`). What needs a yes from the person is in invariant 5; do the rest of your own without a question.
20. **Structure from memory.** Before you plan or change how a project is laid out (a new volume or base, splitting one, an environment, a desk, which base a kind of work starts from), read every section of the `memory`, and `plan` and `open-work` for a change already agreed, proposed or half done. Build on what it names and say where the plan departs from it. A layout it does not name is new: say so to the person. A proposal waiting for a yes goes in `open-work`; once agreed it becomes the `plan`; `volumes`, `environments` and `desks` change only once the thing exists.

## Three budgets

- **Context.** The tokens of your session. A hand-off to another agent costs a full explanation; one long session costs compaction and drift. Delegate only work that is independent, parallel and verifiable. Continue unfinished work in the same session; a later session starts from the volume and the memory.
- **Infrastructure.** Quota slots and running compute. Defaults for a person: 5 workspaces, 2 environments, 5 capsules, 20 snapshots, 100 GB of disk. Idle stops are automatic (a desk and its workspaces after 30 minutes without use, its environment 5 minutes later when no other awake desk uses it), so manage slots and storage, not uptime. Use is a tool call, an open connection, or a running process in `process` `list`: kill what you no longer need ("How to work", 8).
- **Storage.** Each fork and each snapshot is copy-on-write: free at birth, it grows as it diverges. A stopped workspace still counts its disk and its slot, so it is a pause, not a place to keep work. Delete what you will not use again (convention 10).

## What to do, and what it costs

| You want to | Do | It costs |
|---|---|---|
| Run one command cleanly | `capsule` `create` with `from_workspace` or `from_snapshot` | 1 capsule slot for its lifetime; nothing after |
| Test this exact state, uncommitted work included | `capsule` `create` with `from_workspace` | 1 capsule slot; the workspace is not touched |
| Keep a server up while you work | A background process: `exec` with `detach: true`; check it with `status` each turn; `process` `kill` it when done | It keeps the workspace awake while it runs; it ends with the workspace |
| Guard against a forgotten resource | `ttl_secs` on `workspace`, `env` or `netgroup` `create`, and on `workspace` `fork` | Nothing; a backstop only (convention 11) |
| Edit and run code against real services | A workspace in a desk that is connected to the environment | 1 workspace slot; storage grows with the home |
| Test a change with real traffic, without a deploy | `intercept` `start` to your workspace | Each desk on that environment sees it: say so first, stop it when done |
| Try N approaches at one time | N forks of one base (`workspace` `fork` with `source`), or N capsules; one session coordinates | N slots while they run; delete the losers, keep the winner |
| Break data or services freely | `env` `fork` with `source`, then `netgroup` `connect` to the copy | A full environment slot (2 by default); delete the copy after |
| Keep a ready toolchain | `workspace` `snapshot` with a `volume` name, a `description`, `labels` and a `message` (a volume's first snapshot is tagged `base`), then `delete` (nothing changed since, so it takes no snapshot); later `workspace` `fork` from `name@base` | 1 snapshot slot and the storage of the difference |
| Go back to an older state | `workspace` `fork` from `name@N` (an environment: `env` `restore`); tag a snapshot of it only if others should start there | A new disk in the same volume; nothing else moves |
| Pause inside a session | `workspace` `stop`, or `netgroup` `stop` | Storage and the slot; it is not an end state |
| Start any task | `memory` `read`; take the repository, base, desk and environment from it (`references/memory.md`) | Nothing |
| Start a project that has no memory | Brainstorm with the person, write the initial draft of every section, agree it, then build what it names (use case 13) | Nothing until the draft is agreed |
| Plan or change the layout of a project (volumes, bases, environments, desks) | `memory` `read` of every section first, then propose against it; `memory` `write` when the change exists (convention 20) | Nothing |
| Leave unfinished work for a later session | Commit and push it on a git branch; `memory` `write` with the repository, that git branch and what is left in `open-work`; then `workspace` `delete` | Nothing on the volume |
| Repeat work without a person | `pipeline` `save`, with a schedule or a webhook (`references/pipelines.md`) | The capsules of each job of each run |
| Hand work to another agent | The coordinator's `worker_ask` with the goal and the workspaces; the worker commits, pushes and reports | The context to read the report; no live context is shared |

## Agents and workspaces

An agent is a session. There are two kinds, and both call the platform and workspace tools.

- **Coordinator.** Talks to the person, plans, and gives the work to workers. Owns the three budgets and the lifecycle of every workspace and environment: create, fork, start, stop, delete, snapshots, the volumes and their `base` tags, the memory, a saved pipeline's trigger. It decides which worker uses which workspace. Once a worker holds a workspace, the coordinator leaves its code to that worker: it reads the report, the diff or the test log, and asks the worker when it wants a command run.
- **Worker.** Executes one task on the workspaces the coordinator listed for it; several run in parallel. Full freedom inside that task and those workspaces, nothing outside: it does not create, fork, stop or delete a workspace. It ends with the work committed and pushed (and, only when its task asks for environment state, a snapshot onto the branch the task names) and a report.

**A workspace is a tool, not an agent.** It is where code runs and where code and system state are kept; it exposes its running processes and its files to read and edit. Nothing ties an agent to a workspace: a worker may use several, and the coordinator may use any. Two workers in one workspace overwrite each other, so the coordinator gives each parallel stream its own workspace, usually a fork of the base, and splits the files clearly when two must share one.

In the Kode runtime the role skills `coordinator` and `worker` give each role's own tools. On a host with one agent and no way to start another, that agent is the coordinator and does the workers' work itself (below). `references/permissions.md` gives each tool action for each role, and `references/models.md` the model class for each agent: the coordinator on a strong model, workers with a clear task on a standard or light one.

Topologies. **Solo:** one agent, one workspace; the default. **Conductor:** one agent drives many workspaces or capsules that need no memory of each other (parallel experiments, a test matrix). **Delegation:** the coordinator gives each worker a task and its workspaces; the work is independent, parallel and verifiable, and the hand-off is an artifact. **Pipeline:** the work repeats or follows an event; make a proven workflow a saved pipeline.

**Plan centrally, execute in parallel.** When work is split, the coordinator first writes one plan file with the contracts between the streams: names, fields, arguments, limits, and who owns which files. It puts the file in the base workspace, makes one fork of the base for each parallel stream, and gives each worker a task that names its workspaces, its files and its "done". Workers never negotiate with each other; a gap in the contract goes back to the coordinator. The coordinator integrates the results in a fixed order and runs the whole test set once. Then it ends the session as convention 16 says. `references/planning.md` gives the method and a template of the plan file.

You make the plan and you execute it: say the topology in one line, then build it. When no use case fits, compose from the primitives: a snapshot is a commit of a whole machine or a whole system, a tag is a name you move onto a good one, an intercept is a swap of one service for live code, a capsule is a function call with a file system. Ask what becomes possible when these cost almost nothing, and leave only what a person can read.

## When you cannot delegate

An agent with no tool that starts another is the coordinator and does the workers' work itself. It holds both columns of `references/permissions.md`; the human gate for what cannot be undone stays.

1. **Topologies.** Solo, Conductor and Pipeline work as written. Delegation is out: do not plan work for workers that cannot exist, and do not wait for a report that nobody will write.
2. **Parallel work.** Capsules, background processes and pipelines still run in parallel. One context thinks, so keep the plan short and finish one thing before the next.
3. **Context and hand-off to yourself.** Nobody else absorbs noise: push a long or noisy run into a capsule or a background process and take back only the exit code and the end of the log. Write the task before the work and `REPORT.md` at the end anyway: they carry the work across compaction, and inside the snapshot into a later session.

## Device workspaces

A device workspace runs on the person's own Mac, in an operating system sandbox, and its folder is an ordinary folder there. `workspace` with `action: "create"` and `device` (an id `dev-…` from the `devices` tool) makes one in the desk; without `device` the workspace is a cloud one. The device must be online and active in the desk's team; when it is not, hand the person `kode start` or `kode devices connect TEAM`: you have no shell on the Mac and cannot start its service. It reaches the desk's environment only through `KD_ENV_{SERVICE}_{PORT}` (set to `127.0.0.1:{port}`), never by a service name. A device snapshot (`dsnap-…`) lives on that Mac and is not a volume snapshot: it has no `name@N`, no tag and no label, so invariants 3 and 4 and the memory's volume list are about cloud workspaces. `references/devices.md` gives the sandbox, the access names and the limits; read it before you create one.

## Hosts

Which tools you hold depends on the host; `references/setup.md` says which host serves which. A call acts in the netgroup its optional `netgroup` argument names (id or name), else in your `main`. Use a tool, not a command. Two things have no tool: connecting a provider (the web console) and `kode env`, which names the services of every netgroup on the laptop: give the user the exact command.

## How to work

1. **Orient first.** Follow convention 15, then `netgroup` `list`, `workspace` `list` (the owner's workspaces; `thisDesk` marks this desk's) and `env` `get` of the desk's environment, before any create. Say in one line what exists.
2. **Scope is this desk.** The tools reach everything of the owner; a task is about this desk's workspaces and environment unless the person names another object. Outside the desk, act only on an explicit name or id.
3. **Reuse for the same job; fork for isolation.** Inside a session, a workspace that holds the repo, an environment that runs the app, a desk on it: use them. Create what is missing, and fork when the work must not disturb the original. Name each object in the answer.
4. **Derive the set-up from the repository.** Read `docker-compose.yml`, `.env.example`, `README`, `Procfile`, `package.json`, `go.mod`, `pyproject.toml`, `Cargo.toml`: they give services, ports, variables and packages. Ask the user only what the repo does not say (which registry, which environment to share).
5. **Wait with `wait: true`.** Create, fork, start and `run` start take `wait: true` and answer when the object has settled, or at `soft_ms` (default 20000 on a remote connector; 25000 in the harness) with `{promoted: true, id, kind, poll_after_ms}`: then call the `wait` action of the `kind` tool (`netgroup`: `get`), and for `kind: "process"` loop `process` `wait`. A `wait` that answers `timed_out: true` is called again. A remote connector waits at most 20 s a call, or 40 s when the client asks for progress (Claude Code does; a cut call says `clamped`): pass `timeout_ms: 40000` to a `process` `wait` there. A `failing` service needs its `message` and a fix, not more waiting. `references/tools.md` gives the protocol and the limits.
6. **Packages are tools; services belong in the environment.** No database, queue or broker in a workspace. `references/services.md` gives image, ports and mounts.
7. **Service data.** A service that writes data gets a mount in the same call that creates it. A service without `mounts` loses its data on each restart, and data written before a mount is lost. Example: `{"name": "db", "image": "postgres:16", "ports": [5432], "mounts": [{"folder": "pg-data", "path": "/var/lib/postgresql/data"}]}`. A service that keeps all its data in another service needs none: say so.
8. **Processes.** Long-lived work is a background process: a dev server, watcher, build or test suite that outlives its call starts with `exec` `detach: true`. Never start one with `&`, `nohup`, `setsid`, `disown` or a tool's own daemon flag inside an exec, unless you mean it untracked: it is not listed, keeps nothing awake and ends with its exec. A running listed process keeps the workspace and its netgroup awake, so `process` `kill` what you no longer need. Cases, right then wrong (`references/processes.md` has them in full): a dev server is `exec {cmd: "npm run dev", detach: true}`, then `process` `output`, then a call to its port, never `npm run dev &`; a long build or test is `exec {cmd: "cargo test > ~/notes/t.log 2>&1", detach: true}`, then `process` `wait` with `since`/`since_err` until it exits, never a `sleep 30; tail` loop or `nohup cargo test &`; a watcher is a background process and a database a service of the environment; a daemon-style tool runs in its foreground mode (`gradle --no-daemon`) as a background process; untracked on purpose is only a helper inside one command (`./server & sleep 1; curl …; kill %1`), said so; what runs is `process` `list`, never `ps` in an exec. Read it with `process` `output`: at most 64 KiB a stream per answer, 16 KiB to an MCP client such as a remote connector, though a workspace on an older tool server answers up to 64 KiB until it restarts (`truncated: true`: call again from `next`), `max_bytes` sets that cap (1 KiB to 1 MiB), `head`/`tail` keep lines. List what runs with `process` `list`; `ps` in an `exec` sees only that exec's own processes. Confirm that it listens on its port before an intercept. `process` `kill` stops it when done. At most 32 processes. A crash, a workspace restart or stop and a change of the environment's state arrive as `notices` after the answer of a later tool call, so do not poll for them. An exited process is never restarted; one killed by a workspace stop is relaunched only if its `exec` passed `relaunch: true` (pass it for a dev server that should come back). `references/tools.md` gives the states and the notice protocol.
9. **Intercept etiquette.** In an environment of your own, intercept freely. In a shared environment, say which service you take before you take it, one workspace per service, and stop it when done. Copy the environment for data changes, risky migrations and experiments ("Pick the shape", 4).
10. **Code in and out.** Clone over HTTPS through the owner's connector; never put a token in a URL. A push from a workspace goes to github.com with the person's linked GitHub account and a connector that may write. When a push is refused (`link your GitHub account to push: …`, `connector {name} can only read`), tell the person and say where the commits are (the workspace and its git branch), so the work is not lost when the workspace goes; hand them back as a file when asked. Do not look for another credential. Stage only the files you changed (`git add <paths>`); never `git add -A`, `git add .` or `git commit -a` after a build, an install or a ship. Never commit dependency or build folders (`node_modules`, `target`, `dist`, `build`, `.venv`, `__pycache__`) or other generated output. Look at `git status` before every commit. An installed `node_modules` once went into a routine commit (12,521 files) and slowed git in every workspace; CI now rejects such pushes.
11. **Task board.** When the `task` tool is present, it is how the person follows the work: `add` a task for each step of the plan, set it `running` before you start it and `done`, with `verified`, when its check passed.
12. **Quota and errors.** A `409` that names a limit does not pass on a retry: free something of your own, or report it. A raise is `request_create` with a `reason`, from the coordinator, and the answer to the user says that it was asked. A pipeline job refused only by the `capsules`, `cpu` or `memoryGb` quota waits up to 30 minutes (`waiting for quota: …`) instead of failing. `references/errors.md` gives the action for each error.
13. **Answer shape.** Result first; then the objects created, removed and kept, each kept one with its state and its reason; then the next step. Never a dump of tool output.
14. **Argument errors.** A call with an argument the action does not take is refused with `unknown argument` and the list the action takes. Read the list, fix the call, and call once more. Do not retry the same call, and do not drop the argument and carry on: the object you get would not be the one you asked for.

## Pick the shape

| Shape | Use when | Build |
|---|---|---|
| 1. One standalone workspace | A library, CLI, script, or a fix that needs no running service | `workspace` `fork` from the project volume (first session: `create` with packages from the repo); clone through the connector |
| 2. One managed workspace, desk, environment | One component that needs real services | `env` `create` with the services (or reuse); a desk on it; the workspace in the desk |
| 3. One managed workspace per component, one desk | A change across `web`, `api` and `worker` | One environment with every service; one desk; a workspace per component; each intercepts its own service |
| 4. Copies | Data changes that can break things, experiments, a second git branch, PR review in a shared environment | `env` `fork` with `source` for the environment; `workspace` `fork` with `source` for a copy in the desk, one per git branch or approach |

The example app: a shop with `web`, `api`, `worker`, `db` (Postgres) and `cache` (Redis). Ask in order. Does the work need a running service? No: shape 1. How many components change? One: shape 2; several: shape 3. Would it disturb a shared environment, or try several options? Yes: shape 4. Is it a one-time check? Use a capsule, not a workspace. Only a managed workspace reaches the environment, and a fork made in the desk is managed: "two features at once against the services" is two managed workspaces in the desk, the second a fork of the first.

## Tools

The tools act on one desk. Most tools are one per resource: `action` picks the verb. Every code, run, package and image tool takes `workspace`, the id of a `ready` workspace. `references/tools.md` lists every tool with its actions and arguments, and the ids and states of each object; `references/permissions.md` says who may call each action. Tools take the id or the name; write the name to the user. `volume` `get` takes the id or the name; `tag`, `untag`, `describe` and `rename` take the name. `workspace` and `env` `fork` take either `source`, a live workspace or environment to fork, or `snapshot_id`, a snapshot reference (`name@base`, `name@N`); `create` makes an empty one. A fork never merges back into its source: its code leaves through git, its state through a snapshot with a tag of its own. `env` `restore` puts that same environment back on a snapshot.

## Reads, lifecycle and deletes

- **What do I have:** the orient calls, plus `env` with `action: "list"`.
- **Status:** `workspace` or `env` with `action: "get"` or `"wait"`. Intercepts in force: `env` `get`, `services[].interceptedBy`.
- **Logs of a service:** `service` with `action: "logs"`, `name`, and `tail`, `since`, `previous` (after a crash). It names the workspace when an intercept holds the service.
- **Start and stop:** `workspace` and `env` with `action: "start"` or `"stop"`. Before restarting a stopped `workspace` or `env`, read `stopped_reason`, `stopped_at` and `hint` from `get`: an `idle` stop starts again on use (a start, a create in the desk or a connect wakes an idle desk), an explicit stop stays stopped. A stop is a pause inside a session (invariant 2). A `snapshot` takes no `wait`: it answers when the snapshot is ready. On some hosts `netgroup` `stop` also stops your own tools (`references/setup.md`): make it your last call.
- **Delete:** invariant 5 decides. What you created: persist it if it has value (push code; a snapshot of its volume only for environment state), then the `delete` action of `workspace`, `env`, `capsule` or `snapshot` (an untagged snapshot nothing needs), and say what you removed. `workspace` `delete` takes no snapshot by default and refuses, naming the difference, when packages, image or variables changed since the snapshot it was made from; `save: true` snapshots and deletes only once that snapshot is ready (`tag: X` tags it; a failed snapshot deletes nothing; `promoted: true` means it is still being written: call `delete` again); `skip_snapshot: true` deletes with nothing saved, the difference included. A capsule or device workspace is deleted without one. A volume is not deleted to end a session (invariant 4). What you did not create: list the targets by name and call only when the user named them, or after a yes. A refusal is final.

## Setup and recovery

Act on the symptom you see.

| Symptom | What to do |
|---|---|
| No Kode tool at all (no `netgroup` or `workspace` under any prefix) | Do not guess and do not call an API. Tell the user the five steps of `references/setup.md`. Never run the installer or the login yourself unless told. |
| A tool answers ``not logged in — run `kode login` `` | Tell the user that command, then to restart the client. |
| `403 your access to TEAM is paused` | A team admin must restore access. Stop. |
