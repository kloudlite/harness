# Tools

One tool per resource. `action` picks the verb; the arguments below are the union over the actions, and a call that omits one an action needs is refused with that action's schema. `workspace` is a `ws-` id or a name of a `ready` workspace, `env` an `env-` id or a name. Create, start, restore and `run` start take `wait: true` and `soft_ms` (default 25000, 5000 on a remote door; at most 600000): they answer when the object has settled, or with `{promoted: true, id, kind}` at `soft_ms`; call the `wait` action of the tool named by `kind` (`desk`: `get`). A `wait` action takes `timeout_ms` (default 25000, at most 900000) and answers with `timed_out: true` at the limit: call it again. `exec` and `container_build` hand off the same way with kind `process`: loop `process` `wait` with `since` and `since_err` set to the last `next` and `next_err`. A `process` `wait` on a finished process stays listed with its output readable for 24 hours (the latest 200); an id that ended before that or never existed answers `state: "gone"`. The loop applies when a `promoted` answer arrives; a client that waits on MCP tasks waits on its own and never sees one.

## Ids and states

| Object | Id starts with | States |
|---|---|---|
| Workspace | `ws-` | `creating`, `ready`, `stopped`, `error`, `deleted` |
| Environment | `env-` | `creating`, `running`, `stopped`, `error`, `deleted` |
| Desk | `desk-` | `running`, `starting`, `idle`, `stopped` |
| Capsule | `cap-` | `phase`: `pending`, `starting`, `running`, `terminated`; with `reason` `Exited`, `exit_code` is the result |

Get ids from the `list` actions of `workspace` and `env`, or from `desk` `list`. Tools take the id or the name. A volume reference is `name@<branch>` (`shop-code@base`), `name@N` (a storage commit), `name@latest` (the newest commit), `name` (its `base` branch, else its newest commit), or a snapshot id; a branch reference checks the branch out, the others are detached; workspace `restore` takes one in `snapshot_id`, env `create` in `source`, a capsule in `from_snapshot`. A desk goes `idle` after 30 minutes without use, and its workspaces stop; a start, a create in the desk or a connect wakes it, and the next tool answer reports each workspace restart and stop that happened while idle. What the user stopped stays stopped.

## Desk

| Tool | Arguments | Answers |
|---|---|---|
| `desk` | `action`, `team?`, `name?`, `environment?`, `ttl_secs?`, `desk?`, `wait?`, `soft_ms?`, `clear?` | `list`: your desks, each with id, name, team, environment. `create` takes `environment` to connect one and moves nothing. `connect` takes `desk` and `environment` (id or name; `null` disconnects). Every other tool's call acts in the desk its `desk` argument names. `start`, `stop`, `delete`, `ttl` (`ttl_secs` 600..2592000, or `clear`) |

## Workspaces

| Tool | Arguments | Answers |
|---|---|---|
| `workspace` | `action`, `workspace?`, `name?`, `image?`, `packages?`, `team?`, `source?`, `task?`, `device?`, `snapshot?`, `access?`, `snapshot_id?`, `ttl_secs?`, `clear?`, `message?`, `volume?`, `description?`, `labels?`, `branch?`, `skip_snapshot?`, `wait?`, `soft_ms?`, `timeout_ms?` | `list`, `get` (state, `stopped_reason`, `stopped_at`, `hint` of a stopped one, `restarts`, `packages_missing`, packages, volume, `restart_required`), `create` (`packages` are top-level nixpkgs names such as `python3` or `nodejs_22`, optional `@version`, never nested paths like `python3Packages.x`: Python libraries go in through `uv` (`packages` `add` `uv`, then `uv venv .venv && uv pip install <lib>`); a managed workspace in a desk; with `device` a device workspace on the person's own machine, which must be online and active in this team; with `source` a copy that joins the desk, and for a device workspace `snapshot` names the snapshot to clone; `ttl_secs` sets the TTL in the same call), `restore` (a new workspace from `snapshot_id`, a volume reference such as `shop-code@base`, which checks out `base`; `name` is required; it takes no `task` and no `ttl_secs`: restore, then `ttl` in the same turn), `start`, `stop` (answers the stopped state; `wait: true` waits for stopped, not ready), `restart` (to read new variables; answers the object with `restart`, the new entry of `restarts`, once `restart_required` clears, or `null` and a `hint` at `soft_ms`), `delete` (snapshots onto the checked-out branch, usually `base`, which advances, waits until the commit is ready, then deletes; so delete from the clean merged default branch with a passing build; `branch: "wip-<topic>"` saves onto that branch instead; `skip_snapshot: true` deletes a throwaway workspace with nothing saved; a workspace with no branch checked out (a clone, a detached restore) is refused until it gets one of the two, and an unnamed volume takes the workspace's name unless `volume` names it; `message` defaults to `before delete of <name>`; a failed snapshot deletes nothing; `promoted: true` means the commit is still being written and nothing is deleted yet: call `delete` again, which finds that commit and takes no second one; the answer's `saved` says where the commit went (`base is now v3 (was v2) of volume shop-code`) or that it is detached and the `volume` `branch` call that fixes it; capsules and device workspaces are deleted without a snapshot), `wait`, `ttl`, `snapshot` (`volume` names the volume on its first push: always pass it then, or the volume takes the workspace's name; a clone or a restore saves into its source's volume, so drop `volume` there; `description` says what the volume holds and what it is for; `labels` are up to 8 words for finding the volume, such as the project name; a later value of either replaces the stored one; the snapshot is a storage commit that advances the checked-out branch; `branch` puts it on that branch instead, created or moved there, and checks it out (`branch: "wip-auth"`); the answer has `branch` (the branch now at this commit, or null) and `detached` when the checked-out branch had moved since; the first commit of a volume makes `base`; `message` says what changed; it takes no `wait` and answers when the commit is ready) |
| `workspace_vars` | `action`, `workspace`, `variables?`, `replace?`, `restart_on_change?` | `get`: the stored variables; a secret shows as its reference. `set`: merges; `replace: true` replaces the set; a secret is the whole value `${{ secrets.NAME }}` |

## Code, run, packages, images

| Tool | Arguments | Answers |
|---|---|---|
| `read` | `workspace`, `paths` | Files with line numbers (`read`, `write`, `edit`, `glob`, `grep`, `transfer` and `download` reach only `~/workspace`, every path relative to it; `exec` reaches the rest of the home); a PNG, JPEG, GIF or WebP comes back as an image you see (5 MB at most; a bigger PNG or JPEG is downscaled to fit) |
| `write` | `workspace`, `path`, `content?`, `content_b64?` | Creates or overwrites one file: `content` text, or `content_b64` base64 for a small binary file (10 MiB). To copy a file between workspaces use `transfer` |
| `download` | `workspace`, `path` | `{url, uri, name, size, mime}` and a `resource_link`: `url` opens one file (200 MB at most) in the Kode console once the person is signed in, and carries no credential; an MCP client reads `uri` with `resources/read` (7.5 MB at most). Give the person the `url` |
| `transfer` | `from`, `to`, `overwrite?` | Copies one file (200 MB at most, any bytes) from `{workspace, path}` to `{workspace, path}`, both yours, possibly the same workspace; the bytes go between the tool servers, never through you. An existing destination is refused unless `overwrite`. Answers `{from, to, bytes}` |
| `edit` | `workspace`, `files` | Exact text replacements, all or none |
| `glob`, `grep` | `workspace`, pattern | Matching files, matching lines |
| `exec` | `workspace`, `cmd`, `cwd?`, `env?`, `soft_ms?`, `detach?`, `head?`, `tail?`, `max_bytes?`, `quiet?`, `notify?` | Output and exit code, at most `max_bytes` a stream (64 KiB by default, 16 KiB to an MCP client such as a remote door, though a workspace on an older tool server answers up to 64 KiB until it restarts, held to 1 KiB..1 MiB; the end, with `head` the start), `truncated: true` and `id` to page the rest with `process` `output`; secrets masked as `***`; past `soft_ms` (a remote door: default and most 20 s) `promoted: true`, `kind: "process"`, a process `id` and `poll_after_ms`: call `process` `wait` after it; with `detach`, a process id |
| `process` | `action`, `workspace`, `id?`, `timeout_ms?`, `since?`, `since_err?`, `head?`, `tail?`, `max_bytes?` | `list` (every exec, build and watch command; `ps` in an `exec` sees only that exec's processes), `output` (from an offset; at most `max_bytes` a stream per answer, as `exec`, `truncated: true`: call again from `next`; `head`/`tail` keep lines), `write`, `close_stdin`, `kill`; `wait` waits for the exit (20 s at most per call), answers `state`, `exit_code`, the new output and `next`/`next_err`; repeat while `timed_out`; a finished process stays listed with its output readable for 24 hours (the latest 200); an id that ended before that or never existed answers `state: "gone"`; one that a workspace restart killed answers `state: "killed_by_restart"` with `restarted_at`; an exited process is never restarted; a detached one killed by a workspace stop is relaunched (same `id`, output opening `[restarted <time>: <reason>]`) unless `exec` passed `relaunch: false`. Any tool answer can carry a second content item `notices: [...]` (crashed or killed processes, workspace restarts and state changes, environment state changes); the first item is the answer or the error alone |
| `watch` | `action`, `workspace` | `start`, `poll`, `stop`: a file or command watch |
| `packages` | `action`, `workspace`, `packages?` | `list` (also `missing`: entries with no binary), `add`, `remove`, `update`: entries `attr` or `attr@version` |
| `container_build` | `workspace`, `tags`, `soft_ms?`, `max_bytes?` | Builds and pushes to the registry connector; past `soft_ms` (remote default and most 20 s) it hands off like `exec`, kind `process` with `poll_after_ms`; fails with `no_registry` or `unknown_registry` and the connected `registries` |
| `container_push` | `workspace`, `src`, `dst` | Copies an image to more names |

|---|---|---|
| `intercept` | `action`, `env`, `service`, `workspace?`, `ports?` `[{service, workspace}]`, `wait?`, `soft_ms?` | `start` sends the service's traffic to the workspace (kind `env` when promoted); `stop` gives the service back |
| `volume` | `action`, `volume?`, `kind?`, `owner?`, `label?`, `description?`, `labels?`, `branch?`, `version?`, `snapshot?`, `to?` | `list` (`label` keeps only the volumes that carry it; each named row has `description`, `labels` and `branches`, a map of each branch to its commit number; ## Agents (Kode runtime)

The coordinator gives work to workers and a worker answers; no other host serves these two.

| Tool | Arguments | Answers |
|---|---|---|
| `worker_ask` | `worker`, `task`, `workspaces?`, `for?` | Coordinator only. `worker` is a name you pick (1 to 40 lowercase letters, digits or `-`, not `main` and not starting with `ws-`). The first call with a new name starts that worker and needs `workspaces` (ids or names); a later call sends it a follow-up, and `workspaces`, when given, replaces its list. `for` is the id of your own board task that the work serves. It answers at once, with a note when a workspace is also given to a worker that has not finished; the worker's answer arrives later as a turn `[from <worker>] ...`: do not wait or poll |
| `report` | `kind`, `text` | Worker only. `kind` is `done` (finished), `blocked` (cannot go on: say what would unblock you) or `need` (a fact, an action or another workspace from the coordinator or the person; keep working on what you can). `done` and `blocked` end your turn. A worker's workspace tools reach only the workspaces on its list (with one listed, it is the default); another is refused with `workspace {w} is not in your brief; your workspaces: …. Ask the coordinator with report need.` |
