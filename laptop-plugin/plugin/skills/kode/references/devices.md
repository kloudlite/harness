# Device workspaces

A device workspace runs on the person's own Mac, in an operating system sandbox, and its folder is an ordinary folder there. `workspace` with `action: "create"` and `device` (an id `dev-…` from the `devices` tool) makes one in the netgroup the call acts in. Without `device` the workspace is a cloud one, whatever else the call says.

## Rules

1. **Online and active.** The device must be online and active in the team that owns the netgroup. If it is offline or active elsewhere, the create is refused with a sentence that says which; the person runs `kode start` or `kode devices connect TEAM`.
2. **No shell on the Mac.** A device workspace has no ssh, and you have no shell on the person's Mac: do not search for one. Its tools (`read`, `write`, `exec`) reach it through the gateway; they are all it exposes. Anything that needs the Mac itself (`kode login`, `start`, `devices …`) is a command to hand to the person, exactly written.
3. **The sandbox.** `exec` runs in the sandbox: it writes only the workspace folder and its own `TMPDIR` (a tool that ignores `TMPDIR` and writes the per-user temp or cache folder is refused), and it reads only its folder plus the system tool folders (`/Library/Developer`, `/opt/homebrew`, `/usr/local`). The network reaches every host except the Kode API and any that the person denied (an `allow` list from the person narrows it to that list). It never reaches the Mac itself: loopback, the Mac's other local services and the names that `kode` writes into `/etc/hosts` are refused, by address or by name.
4. **Snapshots.** `workspace` `snapshot` takes a copy-on-write snapshot on the Mac (the workspace restarts while it is made). `fork` with `source` and `snapshot` (a `dsnap-…` id) forks it, and the fork joins the netgroup; `fork` with a `dsnap-…` id as `snapshot_id` makes a new workspace the same way. A device snapshot is not a storage commit: it has no `name@N`, no branch and no label, and it lives on that Mac. The snapshot-first rule, "a volume stays" and the memory's volume list are about cloud workspaces; for a device workspace the memory names the repository and the run commands only.
5. **The environment.** A device workspace reaches its netgroup's environment only through `KD_ENV_{SERVICE}_{PORT}` (and `KD_ENV_{SERVICE}` for a service's first port), set to `127.0.0.1:{port}`. Read them with `exec` `env | grep ^KD_ENV` and connect to that address, for any protocol. Names such as `db`, `db.main` or `notes.mac-test` do not resolve in the sandbox, and the proxy refuses them with `403 not in the allowlist`; do not try them, and do not try another workspace's name either. A service added after the workspace started gets its variable after `workspace` `restart`. The forward uses the tunnel of the workspace's own netgroup, whichever netgroup the laptop picked. A workspace reaches only the services of its own netgroup, never another's, and never another workspace's forward.
6. **Picking a device.** `devices` lists the machines with `online`, `enabled` and `account`: pick one that is online and whose `account` is the netgroup's team. An agent cannot start the Mac's service or connect a device to a team; hand the person the command. A name is unique within its account, and these names are reserved in every account: `ws`, `env`, `api`, `admin`, `system`, `kd`, `bld-…`, and anything that looks like an id.
7. **Extra access.** `create` names extra sandbox access in `access` (for example `["xcode", "user-temp"]` for an iOS build). The person defines the names on their Mac (`kode devices access list` shows them); an undefined name keeps the workspace from starting with `AccessUndefined` and a sentence that names the command which defines it. Hand that command to the person. Built-in names: `xcode` (Xcode and its build output), `user-temp` (the per-user temp and cache folders), `android` (the SDK) and `pty` (a pseudo-terminal, which `xcodebuild test` needs). Simulator tests need `["xcode", "user-temp", "pty"]`, and the simulator must be booted BEFORE the workspace starts, because its test socket is granted at start. A name that the Mac refuses (`AccessRefused`, for example a keychain or the home folder) is final: do not look for a way around it. Signing and running on a device are not supported; build for the simulator. Package caches need no access, since `~` is the workspace folder.
8. **Files.** A binary file that you want to see or give the person: `read` an image, or `download` for a console link that the person opens signed in (and a resource link that an MCP client reads); `transfer` moves a file between your workspaces.
